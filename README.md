# Win32.ahk

This set of scripts is a "projection" of the Win32 API based on metadata provided by the [Win32metadata](https://github.com/microsoft/win32metadata/) project.

The majority of the code is generated by a script.

This version is for AutoHotkey v2.1-alpha.37.

## Project Structure

The current directory is intended to be the root of the Win32 library. Script files directly within this directory were hand-written and copied here by a script.

Each sub-directory corresponds to a namespace in the metadata, with the `Windows.Win32.` prefix having been removed. Each sub-directory contains:
  - `__Init.ahk`: Allows the directory itself to be imported with `#Import`. The directory module exports all types, constants and functions.
  - `API.ahk`: Contains function definitions.
  - `Constants.ahk`: Contains constants, defined as global variables.
  - `Types.ahk`: Contains struct, typedef, enum, interface and function pointer type definitions.

These files are all intended to be used as modules.


## Usage Example

```AutoHotkey
#Requires AutoHotkey v2.1-alpha.37

#import "Win32\UI.Controls" {*}
#import "Win32\Foundation\Types" {HINSTANCE}
#import "Win32\System.LibraryLoader\API" {GetModuleHandle}

hInst := HINSTANCE(GetModuleHandle(unset).value)
flags := TASKDIALOG_COMMON_BUTTON_FLAGS.TDCBF_YES_BUTTON
TaskDialog(unset, hInst, "Test", "Hello, world!", "This is an example.", flags, "#160")
```


## Functions

If a pair of functions have the `[Ansi]` and `[Unicode]` attributes, the ANSI function is omitted and any `W` suffix is removed.


## Parameters & Return

This applies to parameters of functions and interface methods.

`HRESULT`: Return values of this type are translated to `"HRESULT"` unless they have the `[CanReturnErrorsAsSuccess]` attribute, in which case a `HRESULT` typedef struct is returned. In other words, functions without the attribute automatically throw `OSError` if a failure value is returned.

`PWSTR`: Currently parameters of this type are translated to `"Str"` if they are for input only. See also *Known Issues* regarding MAKEINTRESOURCE.

`[NativeArrayInfo]`: If a pointer parameter represents an array and has its length passed as a separate parameter, the latter is omitted from the external parameter list and its value is derived from the Length property of the array.

`[MemorySize]`: If a pointer parameter has its byte size passed as a separate parameter, usage depends on which combination of in/out it is.
  - **in** or **optional in**: omitted from the external parameter list, value derived from Size property.
  - **optional in & out**: included in the external parameter list, default value derived from the Size property.
  - **out** or **optional out**: currently no translation, but in future the two parameters might be merged.

`[Reserved]`: Parameters with this attribute are omitted from the external parameter list and the function internally passes 0.


## Types

### Replacement Types

`bool` is translated to `Boolean8`, which is simply an alias of `UInt8`. This is distinct from the Win32 `BOOL`, which is a typedef for `int`.

`System.Guid` is translated to `GUID`, implemented in `guid.ahk`.

`UIntPtr` and `UInt64` are translated to their signed equivalent, due to AutoHotkey's lack of support for unsigned 64-bit integers.

`void*` is translated to `Struct.Ptr`. Parameters of this type can take an instance of any struct class, a boxed pointer, or an instance of a pointer class. `Struct.at(value)` can be used to encapsulate an arbitrary numeric value for a `void*` parameter.

A small number of functions refer to WinRT types. These types are translated to `UnsupportedType(name)`, which throws an error when evaluated.


### Typedef

A typedef such as `typedef B A` is projected as `struct A` with a `Value` property of type `B`, except when `B` is `void*` and the type name begins with `H`, in which case `IntPtr` is used instead of `Struct.Ptr`.

AutoHotkey v2.1-alpha.37 allows field values to be passed as constructor parameters, as in `HWND(A_ScriptHwnd)`.


### Enum

An enum type *EnumType* with the underlying numeric type *NumType* is projected as `struct EnumType extends NumType`. The implementation of each function or method shows the enum type in its parameter list, but because `__value` is inherited from *NumType*, return/output values are always of type *NumType*. Input values can be an instance of *EnumType* or an integer.

Each enumeration member (constant) is currently defined as a property of the enum class, with its value being an integer, not an instance of the enum class.

Most constants and enum values in the Windows SDK are not scoped to an enum type (i.e. they're global), so they tend to include a naming prefix which makes fully qualified names like `TASKDIALOG_COMMON_BUTTON_FLAGS.TDCBF_NO_BUTTON` unnecessarily verbose. Future versions of the projection might place these in the module namespace instead, or in a sub-module for more control (e.g. `#Import "UI.Controls:TASKDIALOG_COMMON_BUTTON_FLAGS" {*}`).


### FunctionPointer

Function pointer types derive from this class. `FunctionPointer` itself should not be used directly. For the purpose of explanation, suppose that `PFN` is a subclass of `FunctionPointer`.

A function object `fn` can be explicitly converted to a function pointer of type `PFN` with `PFN(fn)`, or implicitly converted by assigning it to a field or property of that type.

What an API does with a function pointer after it is passed in a function call or placed into a struct cannot be determined automatically, so it is assumed that every function pointer might be retained indefinitely. `PFN.Free(fn)` can be called to release the function and delete the callback. `fn` must be the original function object and `PFN` must be the exact pointer type.

Retrieving the value of a `PFN` field does not perform any conversion; the `PFN` instance itself is returned.

Each instance has a property `p : IntPtr` which contains the callback address. Note that `ptr` is inherited from `Struct`; it returns the address of the function pointer variable, and therefore must not be used directly as a function (i.e. `DllCall(pfn)` will cause instability).


### InterfacePointer

All projected interface pointer types derive from this class. This includes no native virtual methods or reference-counting logic, because some interfaces do not derive from IUnknown.

Each virtual method is implemented as a method, with parameter types hardcoded (not passed by the caller).

Method parameters are subject to some translation, the same as global functions.

Interfaces with a `[Guid]` attribute have a static `IID` property with its stringified value.


### IUnknown

IUnknown has a custom implementation to make COM interfaces easier to deal with.

The constructor accepts a raw or wrapped interface pointer which must already be the appropriate type (QueryInterface is not called automatically). Specifically, it accepts:
  - a `ComValue` of type `VT_UNKNOWN` or `VT_DISPATCH`, in which case AddRef is called.
  - an interface pointer value as an integer, in which case AddRef is not called.
  - `unset` or `0` to represent a null interface pointer.

The method `as(interface)` performs a QueryInterface call using `interface.IID` and returns an instance of `interface` if the interface is implemented, otherwise `unset`.

`__delete` releases the interface pointer.

For example, `IUnknown(comObj).as(IProvideClassInfo)` returns an IProvideClassInfo instance if comObj implements that interface, otherwise `unset`. If comObj is a raw interface pointer, it will be released (making any subsequent access to `comObj` invalid after this point).

`__value` is currently not implemented, so properties of `IUnknown` type cannot be assigned directly.

Parameters of type `IUnknown` (or derived) require an instance of the given type. For example, an `IUnknown` parameter can accept an `IDispatch` instance. ComCall checks the instance's class, not QueryInterface.

Parameters of type `IUnknown.Ptr` may accept a VarRef to receive an IUnknown instance. This is a standard feature of the built-in Ptr classes.

Reassigning or copying the pointer value of an instance without the appropriate AddRef or Release call will cause leak, crashes or program memory corruption.


## Renaming

Names in AutoHotkey scripts are case-insensitive, but in C they are case-sensitive, and some types or APIs have the same name written with different case, even within the same namespace. We currently separate functions from type definitions, so (for example) `socket` and `SOCKET` can both exist with their original names. Import from `API.ahk` or `Types.ahk` to be sure of which one you get.

Name conflicts between two fields in the same struct or two types in the same module are resolved by appending `_1` and `_2`. For example, `YxyCOLOR` has fields renamed to `Y_1` and `y_2`, and referencing `.y` or `.Y` throws a PropertyError (the same as for any nonexistent property).

`#Import "..." {*}` in AutoHotkey v2.1-alpha.37 does not import names beginning with an underscore. To account for this, we currently strip off leading underscores from type names, unless there is already a type with that name within the module (e.g. `_AppEvents` and `AppEvents` both exist in `System.Mmc`).


## Other Issues

Some types are defined multiple times, with each definition having the `[SupportedArchitecture]` attribute indicating which platform the definition applies to. The current implementation drops all definitions which do not apply to x64 (i.e. scripts running on 32-bit will misbehave if one of these structs is used).

Some function parameters of type `PWSTR` should also accept a `MAKEINTRESOURCE(N)` value, but they are projected as `"Str"` and therefore require a string. In most of those cases, a string such as `"#123"` can be used instead. Currently constants such as `IDC_CURSOR` are defined as numbers, but this might be changed.
